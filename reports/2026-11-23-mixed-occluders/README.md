# 設置松明の前に幹と段差があるときの影

木陰の松明は手前の草を照らす。白樺の幹と土の段差が火を別々に隠す場所では、両方の間から見える火の面積に応じて壁や地面の影が濃くなる。RTX 3080 Ti上のMinecraftで、松明4本の自然の白樺林と、土を動かしたり牛を歩かせたりできる白壁の試験場で確かめた。[通常描画の比較](paired-shadows.jpg)・[壁の光の測定](wall-visibility.png)

## 白樺林でどの影を直せるか

白樺林の実際の照明グリッド64³セルと各松明で使われた計算法をゲーム内から読み戻した。前の実験版が簡易計算を使った半影12,144件のうち、11,174件では光路に複数の不透明ブロックがあり、970件では葉と幹が近接していた。薄い葉を実際に光線が横切るケースについては参照値を確定できない。この集計は4灯の固定視点で観測でき、参照に対応づけられた受光点と光源の組に限る。[グリッドの取得](grid.py)・[材質と経路の集計](forest-census.json)

Claude Fableは、受光点ごとに幹を一つだけ選ぶ案について、根元に新しく明暗の筋ができると指摘した。実装を決める前に、単一の直方体として扱える7,468件と、複数の形が必要な3,706件に分けて実測した。切り替わる縦の隣接115組のうち、68組で段差の誤差が2/255を超えて悪化。参照上70.4%から70.3%にしか変化しない壁で、単純な切り替えでは70.4%から33.3%に落ちた。そこで二つの遮蔽物が同時に発光面を隠す面積を計算する方式を選んだ。[Fableへの質問](advisor-question.txt)・[助言全文](advisor-answer.txt)・[受光点ごとの試算](per-point-switch.json)

1 mの区画から円盤形の火までを調べ、光路上の不透明なセルが12個以下で、すべてが二つの中身の詰まった直方体に分けられるとき、その位置と寸法をワールド座標に対応させて保存する。受光点から二つの影を円盤へ投影し、重なる面積を一度だけ数える。ほかの材質やより複雑な形がある場所は既存の材質別光線追跡を使う。計算法の境界では、受光面が斜め隣のセルを通る場合も考慮して重みを連続にする。動物はそのフレームの三角形で、静止物の間から見えている部分をさらに遮る。[世界の形状を保存するシェーダー](../../release/placed-shadow-union-study/shaders/shadowcomp6.csh)・[各画素の影](../../release/placed-shadow-union-study/shaders/lib/local_lighting.glsl)

実際に描画した可視率と、同じ点から8,192本の光線で求めた独立参照を比較した。表示前の可視率を0〜100%で表し、差の絶対値を平均した値が下表の「ポイント」。画面のRGB値には日射、反射、露出も含まれる。[実機での個別数値](forest-polygon.json)

| 白樺林の半影 | 測定件数 | 前の実験版 | 今回 |
|---|---:|---:|---:|
| 参照と対応する全件 | 25,727 | 5.78ポイント | 2.53ポイント |
| 二つの直方体を使った部分 | 8,135 | 11.55ポイント | 2.12ポイント |

この8,135件のうち、二つの直方体がどちらも円盤を部分的に隠すのは3,942件。うち68件は影が重ならず、1,265件は一方の影がもう一方に収まり、2,609件は一部が重なった。2,362件では暗い方の影を一つ選んでも可視率を1ポイント以上高く見積もる。二重に隠れる面積を省いたときに失われる濃淡を、ゲームから取得した入力で定量化した。[形状別の件数](coverage.json)

同一平面上で計算法が切り替わる実画面の隣接画素を縦と横で別々に撮影した。参照自身の変化を差し引いて比較すると、縦106組・横18組のうち、前の版より2/255を超えて悪化した組は両方向とも0。2/255を超えて改善した組は縦24組・横1組だった。横には記録した実際の光線の始点も使った。[縦の測定](forest-polygon.json)・[横の測定](horizontal.json)

## 土と牛を動かす

通常描画を同じカメラで比較した。幹に草ブロックを接したとき、奥の壁45行で左右の輝度差は両版とも平均30.44階調。各行で隣同士の画素がいちばん大きく変わるところは平均15.36階調から3.26階調になった。影の両側の明暗差を保ちながら、境目が滑らかになっている。草を斜めに移した場合、もう一方の壁の縁45行では、同じ指標が9.94階調から1.11階調になった。[実画面と3倍拡大](paired-shadows.jpg)・[領域と表示輝度の測定](display.json)

隔離した試験場の草地に松明を設置し、白樺の横に草ブロックを足し、斜めに移し、牛を光路の内外に通した。最後に草ブロックと松明を順に撤去した。草ブロックを外すと、元の半影6,217地点で可視率の8ビット値が元に戻った。牛が手前で影を落とした5,261地点でも、通過後にすべて元に戻った。4.62 m歩いた牛の反対側の壁415地点では通過中も変化がゼロ。松明を外した後は計測画像上の対象灯の評価回数がゼロになった。[8場面の実行記録](step-polygon-meter/complete.json)・[参照値と復帰の測定](step-polygon-meter-score.json)・[通常描画の同じ8場面](step-polygon-ordinary/complete.json)

途中の試作では、段差を斜めに移したとき、暗い壁の一地点で火の50.6%が見えるという誤った結果が出た。特殊な位置で重なる二つの影の境界を、符号付き面積の計算が二重に数えていた。凸多角形を切り詰めてから円との共通面積を計算するよう修正。同じゲーム内画素が3.5%になり、8,192本の光線による3.6%に近づいた。斜め配置の壁13,590地点を直接GPUに再入力すると、倍精度の参照から2/255を超えて外れた地点はRTXで258→0、Mesa llvmpipeで170→0。接した配置13,739地点と、それ以前の40,270入力でも修正後はこの閾値を超えなかった。遮蔽計算だけを調べる検査と、ブレンド・量子化後の実画面は別に記録した。[ゲーム内の縦一列](wall-visibility.png)・[両ドライバでの再現](overlap-test.json)・[独立した倍精度計算](footprint.cpp)

撤去と通過の一致は、各操作のあとに撮影した画面で評価した。設置・撤去の直後から最初の1フレームまでの応答時間は未計測。

キャッシュ単体では、土の設置・撤去、葉への差し替え、消灯、再点灯、光源の順序変化、移動によるアドレス再利用を含む22段階を検査した。各ドライバで848,896組を独立した検査と比較し、56,335回の直方体記録のうち二つを格納したのは2,856回。追加のR32F領域は512×6,144テクセルで12 MiB。先行する二直方体の試作で、同じ白樺林を描くJavaプロセスのVRAMは短時間で1,622〜1,634 MiBだった。[RTX](cache-10_nvidia.log)・[Mesa](cache-50_mesa.log)・[先行試作のVRAM観測](residency.json)

途中の計測専用版には二つの欠測がある。最初の二直方体版では診断描画が遅く、フレーム数が計時の下限に届かなかった。隅の補正だけを入れた別の起動では、操作区間を短縮したため4本を設置する前に準備完了判定が走った。後者は中止して失敗記録を残した。上記の最終画像は通常の設置順で別に完走したもの。[中止した起動](../2026-11-23-torch-density/gp-density-double-box-corners-meter/complete.json)・[最終の4灯確認](../2026-11-23-torch-density/gp-density-double-box-polygon-meter/complete.json)

## サバイバルで同じ白樺に戻る

配布用ZIPで前回の白樺のセーブを隔離コピーから再開した。幹の北側まで歩き、持ち物にあった土を一つ置き、東に回って前回の松明を見た。保存したワールドの領域ファイルから、新しい土、隣の白樺、設置済みの松明、離れた岩陰に残した壁松明と魂のランタンを読み戻した。昼夜と天候は自然に進行し、コマンドは無効。今回の7.52 mと1,496ティックを加えると、3シードの継続経路は87,076ティック（3.62817ゲーム日）、957.60 m。[今回の3枚](survival.jpg)・[保存時のブロックと持ち物](../2026-11-21-animal-light/woodland/soil-step-and-torch/save.json)・[この場所から遊べるセーブ](../../dist/Aqualumen-Birch-Soil-Step.zip)・[累計](playtime.json)

実験版のビルドは `python3 tools/build.py --placed-shadow-union-study`。Minecraft Java 1.21.1、Iris 1.8.8、Sodium 0.6.9、Physics 0.2.0を使い、隔離したRTX環境ではAqualumen Lighting Compiler 0.3.0を有効にした。通常Labは1.8.0を選択している。[シェーダーZIP](../../dist/Aqualumen-Placed-Torch-Shadows.zip)・[NVIDIA用コンパイルMod](../../dist/aqualumen-lighting-compiler-0.3.0.jar)・[使用したZIPとGPUの記録](../2026-11-21-animal-light/woodland/soil-step-and-torch/complete.json)

## 白樺林4灯のフレーム間隔

2560×1440、描画距離12チャンク、RTX 3080 Ti。GPUタイムスタンプを取り除いて、Minecraftが次の画面を描くまでの間隔を記録した。配布用ZIPと直後に動かした前の版の差は平均14.46 ms（22.6%）。外側のZIP圧縮だけが異なる試作の測定でも、同じ方向に差が出た。

| シェーダーと測定順 | フレーム数 | 平均 | P99 |
|---|---:|---:|---:|
| 前の実験版（保存済みの測定） | 147 | 68.43 ms | 74.38 ms |
| 今回の通常描画と中身が同じ試作 | 120 | 83.98 ms | 91.35 ms |
| 今回の配布用ZIP | 128 | 78.41 ms | 84.15 ms |
| 前の実験版（配布用ZIPの直後） | 157 | 63.95 ms | 71.13 ms |

各起動で同じ4本の松明を確認した。[前回の記録](../2026-11-23-torch-density/gp-density-placed-hull-animal-ordinary/summary.json)・[通常描画の試作](../2026-11-23-torch-density/gp-density-double-box-polygon-ordinary/summary.json)・[配布用ZIP](../2026-11-23-torch-density/gp-density-paired-release/summary.json)・[直後に測った前の版](../2026-11-23-torch-density/gp-density-paired-previous/summary.json)

同じルートを専用GPUプロファイラで測り、GPUフレーム平均は前の版58.68 ms、今回72.84 ms。見えている地形の照明を計算する `quad/deferred` が17.56→31.54 msと13.98 ms増えた。静止時に形状キャッシュを更新する `shadowcomp6` は0.0079→0.0108 ms、葉や草を描く `terrain/cutout` は10.90→10.65 msだった。ゲーム全体のフレーム間隔の増加とGPU上の描画負荷増加がほぼ対応する。この場面ではGPUの照明パスを優先して調べられる。[配布版のGPU内訳](../2026-11-23-torch-density/gp-density-paired-release-gpu/summary.json)・[前の版のGPU内訳](../2026-11-23-torch-density/gp-density-paired-previous-gpu/summary.json)

原因をさらに分けるため、隅のブレンドは修正版と同じで、共通面積の計算だけ初期方式にした途中版を、4灯の設置順を確認して測った。平均69.08 msで、隅の補正前の試作69.32 msに近かった。共通面積の計算を差し替えた通常描画の78.41〜83.98 msと差がある。途中版は斜めの配置で光が漏れるため、速度の内訳を調べる対照に使った。[隅の補正だけの計測](../2026-11-23-torch-density/gp-density-paired-corners-cost/summary.json)・[補正前の計測](../2026-11-23-torch-density/gp-density-double-box-ordinary/summary.json)

多角形の頂点を書き戻す作業配列を二つから一つに減らす試作も行った。67,599入力に対する結果はRTX・Mesaとも配布版と全件一致。4灯の平均フレーム間隔は78.08 msだった。今回の配布版との差は0.33 msで、同じシェーダーの別起動で見た変動より小さい。速度向上を判定できないため、配布ZIPには検証済みの二配列方式を収録した。[実装した試作](inplace.py)・[演算の一致](inplace.json)・[実Minecraftのフレーム間隔](../2026-11-23-torch-density/gp-density-paired-inplace-cost/summary.json)

この2回のGPUプロファイル中、松明4本がある約7秒ずつのJavaプロセスのVRAM観測は、今回1,563〜1,621 MiB、前の版1,610〜1,622 MiB。プロセス全体の常駐量は変動する。R32F画像自体の12 MiB増分は画像寸法から別に算出した。配布版のGLSL全37プログラムはRTXとMesa llvmpipeでコンパイル・リンクを確認し、RTXには実ゲームと同じコンパイラ指示を適用した。[常駐量の各観測](residency-paired.json)・[RTXのリンク結果](compile-10_nvidia.log)・[Mesaのリンク結果](compile-50_mesa.log)・[配布ZIPと全場面の照合](verification.json)

Claude Fable 5.2にも、割付を隠して同じ白壁の2枚を見せた。通常倍率では小さい差だが、前の版の壁に細い帯と硬い境界があり、今回の滑らかな方を選んだ。どちらが精密で重いかについては最初に取り違えたため、実際の割付とGPUタイムスタンプを外した14.46 msの差を開示して再評価を求めた。Fableはそれでも画質優先の既定候補に今回の版を推した。通常プレイにかかる費用を比較できるよう、両版を個別のZIPで提供する。[提示した画像](advisor-blind.jpg)・[目視回答](advisor-visual-answer.txt)・[割付開示後の判断](advisor-followup-answer.txt)
