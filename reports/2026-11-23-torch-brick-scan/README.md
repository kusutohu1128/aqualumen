# 松明の半影を保って地形の照明を軽くする

[シェーダーZIP](../../dist/Aqualumen-Torch-Shadow-Rows.zip)をIrisで選べる。比較元は[複数の遮蔽物の半影を扱う画質優先版](../2026-11-23-torch-shadow-integral/README.md)。ビルドは `python3 tools/build.py --torch-shadow-rows`。Minecraft Java 1.21.1、Iris 1.8.8、Sodium 0.6.9を使用した。実機比較では既存のAqualumen Lighting Compiler 0.3.0を有効にした。

## 白樺の葉や幹の角を取りこぼさない仕組み

従来は、地面の一点と炎全体を囲む直方体の中で、2×2×2ブロックの区画をすべて調べていた。今回は高さと奥行きごとに、炎の外縁を含む光の通り道が横切る区画を求める。中心線がブロックを外れても炎の端から出る光が角をかすめることがあるため、各軸に炎の広がりを足し、区画を選ぶ段階では外側に余裕を持たせている。残った区画は以前と同じ順番で扱う。地形と光の円錐の交差、1～2個の遮蔽物の投影面積、3～8個の重なりを調べる64点、材質別の透過率、動物の遮光は以前と同じ計算を使う。[シェーダー](../../release/torch-shadow-rows/shaders/lib/local_lighting.glsl)

32ビット浮動小数の独立した走査試験で、グリッド端、整数境界、軸に平行な方向を含む55,000通りを調べた。区画を訪ねた回数は3,695,606回から754,391回になった。炎の端だけが触れた425,298件を含め、採用される計1,451,353セルの座標と順序は一致した。この件数は試験入力での結果で、ゲーム中のテクスチャ読み出し回数は場面と途中打ち切りで変わる。[試験プログラム](coverage.cpp)・[集計](coverage.json)

## 実際のMinecraftでの半影と編集

同じ場所の面・法線の記録が一致した画素について、松明ごとの可視率を8ビットで比較した。白樺林の4灯、5視点では1,516,904件、幹と牛を含む10段階では992,908件を照合し、可視率、経路フラグ、光が計算対象に入ったかの差は0件だった。白樺林の半影だけでも178,006件を含む。カメラの横移動は2 cm刻み。両方の画像で同じ位置を指さない画素は集計から除いた。[森](forest-comparison.json)・[幹と牛](grove-comparison.json)

牛は4.62 m横切り、暗くなった5,325点は通り過ぎると全点が以前の明るさに戻った。光路の反対側にある452点は変化しなかった。幹を切ると明るくなった11,422点は植え直すと元の値に戻り、松明を外した後の光源評価は0件だった。[編集と復元](grove-edits.json)

## サバイバルの岩陰

前回の白樺のセーブを開き、手持ちの松明で7 m高い野営地へ上り、入口に松明を1本設置した。二本の白樺の松明、岩壁のくぼみにある松明、魂のランタン、新設の道しるべを保存データで確認した。松明の所持数は27本から26本に減った。移動は17.73 m、操作観測は129秒。1600×900・12チャンクで、F3を開いて得た表示FPSは78回の中央値16、範囲8～26だった。ワールド時計は2,797ティック進み、入場後の準備時間は3.6秒。3シード通算は3.969ゲーム日、980.48 m。診断用の固定時刻の撮影はこの通算に含めていない。[ゲーム内写真](walk.jpg)・[再開できるセーブ](../../dist/Aqualumen-Birch-Camp-Path.zip)・[時計と操作記録](playtime.json)

Fableは岩陰の写真から、手持ち松明で石の明暗が弱くなり、壁松明の炎が目立たなくなると指摘した。元画像を拡大すると、右の写真では動く煙が炎の上部に重なっている。両方の画像で同じ場所にある発光部分と、炎の上を動く粒子を分けて調べた。[Fableの所見](field-answer.txt)・[元画像の測定領域と表示輝度](niche-pixels.json)

## 手持ちの松明で石の模様が弱く見える原因

岩陰の同じセーブを別に複製し、天気と時刻だけを固定した。野営地まで歩いたときと同じ座標・向きで、手ぶら、松明、もう一度手ぶらの順に持ち替え、各状態を8.5秒以上待って3枚ずつ撮影した。画面の下端に読み出しを追加し、各領域の同じ96点から表示前のHDR、発光成分、露出倍率、表示色を照合した。表の画面輝度は配布シェーダーの表示符号化を2.2乗で戻した相対値。野営地と白樺を保存したプレイ用ZIPは自然の時刻・天気で再開できる。[診断用シェーダーの差分](niche_meter.py)・[固定した視点とゲームの終了記録](../2026-11-21-animal-light/woodland/niche-hand-repeats/complete.json)

| 左の石壁で測った値 | 手ぶら | 手持ち松明 | 再び手ぶら |
| --- | ---: | ---: | ---: |
| 露出倍率 | 2.000 | 2.000 | 2.000 |
| 表示前の相対輝度の中央値 | 0.0137 | 0.6084 | 0.0137 |
| 表示前の明暗比 P90/P10 | 1.872 | 1.880 | 1.872 |
| 画面に出た明暗比 P90/P10 | 1.847 | 1.227 | 1.847 |

手に松明を持つと壁が明るくなり、最終表示で石模様の明暗が圧縮された。表示前の輝度と露出を使って現在のトーンカーブを再計算すると、左壁の表示色をP95で0.54階調以内の誤差で再現した。壁のくぼみの奥と壁松明の発光部分を比べると、手持ち時も発光部分の表示輝度の中央値は0.737、奥の石は0.501だった。固定した発光部分と壁の明るさの順位はこの撮影で保たれた。次の画質比較では、明るく照らされた石と以前の樹皮の模様をどれだけ画面に残せるかを調べる。同時に、火から離れた暗い道と発光部分の見えを照合する。[チェックサム付き9枚の測定結果](niche-radiometry.json)

## ビルド検査の条件

配布ZIPと試作ZIPで、共通のGLSLはコメントと行頭の空白を除き一致し、ほかのファイルは同一。比較元の配布ZIPはそのまま残した。NVIDIAでコンパイル指示を含まない素のソースを検査した最初の単体実行はCPU時間291秒で中断した。実Minecraftでは同梱対象の別MODがNVIDIAの面光源プログラムにコンパイル指示を入れるため、実機条件に合わせた検査では同じ9本に指示を反映する。Mesaは素の配布ソースを使う。[配布と比較元の照合](verification.json)・[対象の描画プログラム](nvidia-programs.txt)・[素のNVIDIA検査の中断記録](unmodified-nvidia.json)

## Nsight Systemsで実Minecraftを収録

RTX 3080 Tiで岩陰の野営地を開き、地形読み込みとシェーダー準備が終わってから、通常の配布ZIPの描画を約6秒収録した。専用のヘッドレスCageとXwaylandを使い、実ウィンドウは1280×720だった。元のLabとプレイ用セーブのコピーが隔離されていること、Minecraftが使ったOpenGLレンダラー名、プロセスIDと描画スレッド名を照合した。これは表にある1440p・白樺林の比較と別の実行。[Minecraft収録の集計](nsight-minecraft.json)

6.026秒の記録には、Javaの描画スレッドのOpenGL APIイベント35,662件、同じJavaプロセスに対応するGPU側の記録18,476件がある。`glDrawElements`は8,613回、`glDispatchCompute`は1,287回、`glXSwapBuffers`は98回。SQLiteから同じ描画スレッドで時間がかかったOS呼び出しも取り出せた。この設定では50 µs以上のOS呼び出しを記録している。個別のAPI呼び出し時間だけでは、待ちの原因や描画パスごとのGPU時間を特定できない。[Nsight UI用の収録](../../build/torch-brick-scan/nsight-camp-retry2/minecraft.nsys-rep)・[SQLite](../../build/torch-brick-scan/nsight-camp-retry2/minecraft.sqlite)・[再収録用スクリプト](nsight_game.py)

最初のVirtualGL経由ではX11の関数解決で起動が止まり、X11とOpenGLのライブラリを明示しても有効な収録を得られなかった。成功した収録は専用の仮想画面からNVIDIAへ直接描画したもの。Cageと必要な共有ライブラリは一時ディレクトリに展開した。[VirtualGL 3.1.5のライブラリ選択処理](https://github.com/VirtualGL/virtualgl/blob/3.1.5/server/faker-sym.cpp#L273)
