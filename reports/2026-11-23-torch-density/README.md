## 計算の順序を変える試作

白樺の1本目で増えた費用に対し、二つの拡散反射パスの実行順だけを変更する。近くのブロックの同じ向きの面を一つのワークグループにまとめ、同じ半球へ向かう96本のレイを隣のパッチと同じ順でたどる。光のサンプル数、色、参照する地形、光源の更新頻度、二回の反射、書き込み先は従来どおり。固定した入力で二つの出力領域が全画素一致し、カメラ移動・消灯後にも書き残しがないことを検査する。速度の比較には、白樺の消灯・1本・4本と砂州の4本を使い、同一場面の順序を反転して再測定する。無灯時の悪化や、片方の順序だけで得られた改善は配布の根拠に使わない。

## 松明の種類と樹皮

通常サバイバルで幹の裏の魂の松明を回収した。幹の東面に向き、手ぶら、松明、魂の松明、手ぶらの順に持ち替えた。樹皮まで0.52 mの写真では、暖色の松明で中央の木目が淡くなり、魂の松明では縦の濃淡が残った。中央210×185画素で表示輝度の10〜90パーセンタイルは暖色が140〜152、魂が112〜154（8ビットのRGBに輝度の重みを適用）。どのチャンネルも250に達しなかった。樹皮との距離は東面への垂直距離。1.50 mの写真とは角度・画素に写る範囲も違う。[11枚の実画面](oak-light-sources.jpg)・[元画像の測定値](bark.json)

Fableは現行版の画像を見た後、旧映像から疑った「魂の松明で樹皮が白飛びする」よりも、暖色で木目が弱く見えることを優先した。また、松明をしまった後の中央輝度が、最初の手ぶらと比べて24〜31%低く、切り替え直後の画面には目の順応と自然時刻の影響が入ると指摘した。通常プレイでは両方の松明を元の位置に戻して終了。携行品、元の位置に残る2本、観察したオーク原木をセーブから再確認した。[Fableの再評価](advisor-oak.txt)・[設置物と所持品](../2026-11-21-animal-light/woodland/two-flames-oak-r2/save.json)・[森の続きから遊べるセーブ](../../dist/Aqualumen-Oak-Lights.zip)

## 同じ時刻で樹皮の木目を追う

オークのセーブを隔離コピーし、そのコピーだけ昼夜と天候を固定した。設置した魂の松明を一旦回収し、同じ姿勢で手ぶら → 暖色 → 魂 → 手ぶら → 魂 → 暖色 → 手ぶらの順に切り替えた。各状態を8.5秒以上保ち、実際の露出と樹皮の同じ64点の表示前RGBをGPUから取得した。初期時刻は15,746、雨なし、幹の東面まで約0.55 m。計測用ZIPで変更したのは画面に値を記録する最終パスのみ。[7回の撮影と2,535サンプルの照合](settled-bark.json)

| --- | ---: | ---: | ---: |
| 手ぶら（最初） | 15.61 | 0.00077 / 0.00114 / 0.00196 | 33 / 40 / 50 |
| 暖色の松明 | 2.00 | 0.249 / 0.518 / 0.716 | 122 / 138 / 143 |

暖色と魂は持つ順を逆にしても表の値を再現した。表示前の輝度にはどちらも約2.88倍の明暗差が残る。暖色は高い光量が最終パスに入り、画面での明暗差は1.17倍、魂は1.41倍になる。どちらも露出は局所光の下限に達している。さらに同じ露出15.61を両方の入力に掛けて表示曲線だけを計算すると、暖色のP10〜P90は154〜159まで狭まる。手ぶらに戻して8.5秒以上待つと木目の表示輝度も元に戻った。この木で「光を当てた時点で木目が消えた」という仮説は棄却できる。

別の隔離実行で樹皮210×185画素の表示前RGBを全て取得した。8×8の計器と共通する64点の値を照合し、元の露出と曲線で再計算した結果を同時撮影のF2画像と比較した。チャンネルごとの絶対誤差の95パーセンタイルは、暖色と魂で0、手ぶらで2階調。暖色の実画像では木目の明暗比（P90/P10）が1.18。露出を半分にした再計算では1.28となり、暗い筋が読み取りやすくなった。別案では表示輝度に合わせて明部を少し無彩色に寄せた。明暗比は1.25になったが、橙色が桃色寄りの明るい色に変わった。比較画像の右2列は同じHDRデータの表示シミュレーション。[樹皮の比較画像](bark-display-study.png)・[画素の照合](bark-display-study.json)

露出を下げる案を隔離したMinecraftクライアントに実装した。照らされた不透明面の測光点で、一番強いRGBチャンネルと輝度との差を取り、局所光の寄与で重み付けする。視野に明るく色の偏った面が広がったとき、露出を従来の下限から最大もう1段下げられる。既存の順応時間と反射の計算を使う。Fableも比較画像を見て、橙色を保てる露出案を次の実機試験に選んだ。手ぶらの画面まで暗くしすぎないことが条件だった。[Fableの所見](advisor-display.txt)・[試験した測光処理](exposure-study/shaders/composite3.csh)

オークでは手ぶらの露出倍率が15.94、暖色が1.00、魂が1.86となった。逆順でも暖色1.00、魂1.87を再現し、最後に手ぶらに戻すと15.84まで回復した。暖色の同一HDRパッチを元の露出で表示した場合と今回のF2を比べると、木目の明暗比は1.13から1.20、RGB中央値は215/121/47から190/107/42になった。魂の松明の明暗比はどちらも約1.30。これらは試作で実際に立てた位置の画素で、前段の別起動と数値が少し違う。中間色の面・昼・水とガラス・暗順応・光源のにじみの既存GL検査はRTXとllvmpipeで通過した。[試作の実画面](bark-response.png)・[同一入力での比較](bark-response.json)・[RTX](response-nvidia.log)・[Mesa](response-mesa.log)

## VRAMに静的な遮蔽を保存する案

別セッションでの約5秒の観測として、砂州・松明4本でMinecraftのJavaが1.60〜1.63 GiB、GPU全体が3.56〜3.59 GiB / 12 GiB、GPU使用率が89〜94%と報告された。現在も直接照射された面から出る光と、面に届く反射光をテクスチャに書いている。追加候補は、**設置された各松明から静止面の各位置へ届く光の割合**をワールド座標で再利用し、同じ遮蔽の計算を繰り返す回数を減らす方法。葉や色ガラスでは、その割合が色と細かい模様を持つ。速度の収支には参照・更新時間、視点移動時の再利用率、光源や地形を動かしたときに更新する範囲が関わる。現時点でこの方式は未実装。

試作するときの比較地点は、松明が照らす木陰の地面と、幹を挟んだ反対側。併せて、設置した光源の撤去、幹の伐採、動物が横切る瞬間と通過後を元の版と照合する。静止物の遮蔽を再利用する場合も、動物の影はその時点の位置で評価する必要がある。

このPCのapitrace 11.1で既存のEGLトレースを読み、呼び出し2978の `glReadPixels`（16×16、浮動小数RGBA）を確認した。元の収録はMesaの露出検査。Nsight Systems 2026.5.2の既存SQLiteは独立したOpenGLプログラムで、OPENGL_API表に81イベントあった。Minecraftの今回の時間はパック用GPUプロファイラとフレーム間隔の計測による。ShellCheck 0.9.0、jq 1.7、qapitrace、nsys-uiもこのホストに配置されている。トレースは `/var/tmp/aqualumen-devtools.6idHtOHN/` にある。

## Nsight Systemsで実Minecraftを5秒収録

RTX 3080 Tiでプレビュー10を起動し、保存した夜道の道しるべを前に静止した状態をNsight Systems 2026.5.2で5秒間収録した。元のLab・保存元と別のゲームディレクトリを作り、専用のヘッドレスXwaylandで描画した。VirtualGLではNsightのフックと競合した。ウィンドウは1280×720、描画距離12チャンク。QApiTraceやMesaで行った検査とは別の記録になる。[実機の集計](nsight-minecraft.json)・[収録手順](nsight_world.py)

SQLiteにはMinecraftの `Render thread` 1本からOpenGL API呼び出し33,424件が残った。そのうち `glDispatchCompute` は2,101件、`glXSwapBuffers` は190件。Javaプロセス全体のOSランタイム呼び出しは1,795件だった。バッファ交換のホスト側呼び出しにかかった時間は累積3,916.6 ms。GPUワークロードとCPUスケジューリングの収録は無効。これだけでバッファ交換に時間がかかった原因や、通常の1440pでのフレーム時間は決められない。ワールドは正常終了し、元のLabと継続セーブの照合を通過した。[Nsightの生レポート](/var/tmp/aqualumen-nsys-night-native-03/night.nsys-rep)・[SQLite](/var/tmp/aqualumen-nsys-night-native-03/night.sqlite)

NsightのGUIで同じレポートを開き、189フレームのCPUタイムラインとJavaの描画スレッドを確認した。SQLiteの診断は情報8件・警告6件で、CPUスケジューリングの未収録などを含む。[タイムラインの実画面](nsight-timeline.png)
