## 2. 重要な考え方：何が誰の責任で、いつ使えるか

- **「その場で計算した結果は、計算したフレームでしか使えない」設計です。**
  - `ReceiverRadianceVolume.current` は、フレーム番号が完全に一致する場合だけ有効と判定します（`ReceiverRadianceVolume.java:75-77`）。
  - `ReceiverRunPublisher.ready` も同じ判定に依存しています（`ReceiverRunPublisher.java:44`）。
  - 世代（epoch）の中に Iris のフレームカウンタが入っています（`ReceiverRadianceBridge.java:44`）。
  - したがって **receiver を使い続けるには、producer（ワールドの情報を集めて陰影計算し、GPU 用に詰める処理）が毎フレーム走る必要があります**。producer を起動するのは、Sodium の描画呼び出しの先頭に挿した処理です（`ReceiverTerrainMixin.java:12-14`）。1フレームに1回だけ走るよう制限されています（`ReceiverSourceSchedule.java:5-10`）。
- **材質（放射輝度）の扱い:** 光の情報を持てるのは「上に完全な水があるブロックの、上向きの面」だけです。producer は面の向きを `{0,1,0}` に固定しています（`ReceiverRunSourceCapture.java:84`）。一方シェーダーは、レイが入った面の向きと記録された面の向きが一致しないと棄却します（`water_receiver.glsl:119`）。その結果、側面に当たったレイは「形はわかるが光の情報がない」扱いになります。
- **植物の扱い:** ケルプや海草は `UNSUPPORTED` に分類され、セル種別 0（不明）になります（`ReceiverRunSourceCapture.java:51`）。シェーダーはここでレイの追跡を打ち切ります（`water_receiver.glsl:140`）。
- **どのパックで動くかの条件:**
  - 名前が "Aqualumen" で始まるパックならすべて対象になります（`ReceiverPackEligibility.java:9`）。
  - 植物の診断処理などの切り替えは、ZIP ファイル名を直接コードに書いて判定しています（`ReceiverRadianceBridge.java:112-125`）。

## 3. 処理の流れ（水中で上を見たときの反射）

1. **反射のフォールバック:** `gbuffers_water.fsh:433` の `environment = underwater ? scatter : …` により、画面空間反射（SSR）が外れた水中反射は、まず水の散乱光（暗い色）になります。
2. **receiver の参照:** SSR が外れ、かつ `aqualumenReceiverReady` が 1 か 2 のときだけ receiver を引きます（`gbuffers_water.fsh:435-447`）。
3. **receiver の打ち切り条件:** 次の場合は「不明」として返ります。
   - 不明なセル（植物を含む）に当たった（`water_receiver.glsl:140`）
   - 経路が 48m を超えた（`:144`）
   - 窓の外に出た（`:101`）
   - 光の情報がない、または面の向きが一致しない（`:115-123`）
4. **画素の結果:** 不明の場合は 1. の `scatter` がそのまま残ります。光の情報がある場合は Beer 減衰（水中での吸収による減衰）をかけた receiver の色になります。
5. **既存の切り分け結果:** 一方が `scatter`、他方が receiver の色、という境目の画素構成は、過去の実機の分類画像で既に数値化されています。
   - **v94（棄却理由別、near / moving）:**
     - 未対応セル: 123,493 / 261,956
     - 面の向き不一致: 20,985 / 33,933
     - 光の情報なし: 21,647 / 3,975
     - 窓の外へ: 0 / 58,566
   - **v95（未対応セルの内訳）:** 背の高い海草が near で 64,394。ケルプが moving で 136,363。
   - これらは画素数で、表示上の重要度を示すものではありません。また v93〜v95 の間で波の状態が違うため、数値同士を因果的に比べることはできません。
6. **v100 の植物処理は描画に届いていません。**
   - `ReceiverPlantProbe.capture` はセッション中に1回しか走りません（`ReceiverPlantProbe.java:20-21`）。
   - 公開はブロックを抜けた時点で閉じられます（`:239` の try-with-resources）。
   - `completeOwnerCells=0` は測った結果ではありません。`Proof(..., false)` が固定で渡されています（`:178`、`ReceiverPlantCellPublication.java:42`）。
   - ログの `traceAdmission=false` も固定文字列です（`:75,84,194,231,269,307`）。
   - さらに、植物の材料サンプルの日光成分はほぼ 0 でした（ログ 9 行目 `sunRgbSum=1.24E-8`）。理由（深さ約30mでの影マップ遮蔽など）は**仮説**で、確認していません。

  - **確定には、全フレームの producer 時間・GPU タイマー・`capture_motion=false` の実行の3つが必要です。**

## 6. 主な不具合・リスク

1. **水中反射の外側で、光の情報がある画素とない画素が硬く切り替わる。**
   - 植物セル、側面、窓の外の画素がすべて `scatter` になります。v94/v95 の数値で確認済みです。
   - これが「暗い多角形のような外側」の原因かどうかは、見た目の上では**未検証**です。
2. **receiver が「生成したフレームでしか使えない」設計のため、毎フレーム約370ms の producer が必要になっている**（推論）。この設計のままでは、普通に遊べるフレームレートにはなりません。
3. **パック名による判定がもろい。**
   - "Aqualumen" で始まる名前ならすべて対象です。
   - もし physics 0.3.0 系を通常プレイに入れると、0.6.0 パックでも producer が走る**可能性があります**（照明の取得条件次第で、未確認）。
4. **ドキュメントが実態に追いついていない。**
   - v100 についての記録がありません。
   - `RECEIVER_FIELD.md` の冒頭は v42 時点の "not adopted"（不採用）のままです。

## 7. 次に勧める実験（実行はしていません）

**目的:** 「receiver の対象範囲（植物・側面）を広げれば、暗い外側は目に見えて改善するのか」を先に判定する。

**手順:**
- 波の時間（`frameTimeCounter`）を固定する。
- near と moving の同じ姿勢で、**同じフレームの**最終画像と、v94/v95 形式の分類バッファを同時に保存する。
- 外側（Fresnel ≥ 0.9999 の画素）について、分類ごとに表示後の輝度の分布を比べる。

**棄却条件:**
- 「光の情報あり」と「フォールバック」の平均表示輝度の差が見分けられない程度（例：ΔL < 0.02、またはΔE < 2）の場合。
- または「光の情報あり」の画素自体が `scatter` と同じくらい暗い場合（30m 級の経路では Beer 減衰で暗くなる）。
- この場合は「範囲を広げれば外側が直る」という仮説を棄却し、外側の暗さはおおむね正当な深い水の全反射だと扱います。注力先は窓の縁と時間的な安定性に移します。

**仮説が支持された場合:**
- 植物の完全な所有証明（大規模な作業）より先に、**側面の光の情報を本物として生成する**、範囲の小さい修正を試します。成果は理由 42・9 の画素数の減少と見た目で評価します。

### まとめ

水中で上を見た反射は、地形の上向きの面だけが実機で使われています。v100 の植物処理は、データを集めて GPU に送るところまでで止まっており、描画には使われていません。外側が暗いことの一部は、深い海では物理的に正しい見え方です。一方で、植物や側面に当たった画素が暗いフォールバックに切り替わることは数値で確認されています。それが見た目の主な原因かどうかは未確認です。FPS が約2なのは、毎フレーム約0.37秒かかる producer が主因だと推測されますが、断定はできません。次は、波の時間を固定し、同じフレームで最終画像と分類画像を比べる実験をお勧めします。その結果で「植物と側面への対応」に進むべきかが判断できます。目標全体はまだ達成されていません。
