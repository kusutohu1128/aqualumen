# 洞窟の露出溶岩：有限面光源タイルの検討（Claude、コード解析と CPU 数値計算）

**この文書の位置づけ**：1.8.0 のコード読解と、CPU だけで動く光学参照計算の記録です。Minecraft、GPU、ウィンドウはいずれも使っていません。`release/shaders`、`dist/`、通常インスタンス、Git には触れていません。**本番には何も変更していません**。ここで「提案」と書いたものは、どれも未実装です。

同じフォルダの `README.md`、`baseline-180/`、`captured-*`、`area-shader/`、`basin.py`、`measure_wall.py`、`natural-pool.json` は、並行して実ゲームの計測を行っている別エージェントの成果物です。私はこれらを読み取り専用で参照しただけで、変更していません（使った入力は SHA-256 で `receipt.json` に記録しています）。

逆アセンブル結果は `build/lava-light-study/javap/` に置いたままです（`build/` は gitignore 済み）。マッピングのライセンスは「完全かつ無改変のマッピングの再配布」を禁じているので、Minecraft や Iris のコードはこのレポートに転載していません。結論の根拠になる定数だけを以下に引用します。

- 溶岩の発光量は、どの状態でも 15（`Blocks.LAVA` に渡すラムダ `dga.O` が `bipush 15` を返す）
- 源ブロックの量は 8（`LavaFluid$Source.getAmount`）、高さは `amount/9`（`FlowingFluid.getOwnHeight`）で 8/9 = 0.8888889。真上が同じ流体なら 1.0（`LiquidBlockRenderer.MAX_FLUID_HEIGHT`, `FlowingFluid.getHeight`）
- オーバーワールドでは 1 ブロック流れるごとに量が 2 減る（量 8→6→4→2）。水平に探す距離は 2。Nether などの ultrawarm 次元では、それぞれ 1 と 4
- `ItemBlockRenderTypes.getRenderLayer(FluidState)` は、水以外の流体を `RenderType.solid()` に割り当てる。そのため溶岩は、影パスでは `shadow_solid`（`LOCAL_SOLID`）を通る
- Iris 1.8.8 の `MixinChunkMeshBuildTask.iris$onRenderLiquid` は、流体にも `beginBlock(blockStateId(fluidState.createLegacyBlock()), …, blockState.getLightEmission(), 位置)` を呼ぶ。つまり溶岩の頂点には block.properties の ID と `at_midBlock.w = 15` が届く。実ゲームで読み取った面と四隅の高さ ≈0.888（別エージェントの `captured-shore-slots/faces.json`）とも整合する

## 2. 1.8.0 の本当の制約

**溶岩は Aqualumen の局所光モデルに一度も入りません。** 原因は四つが重なっていることです。

1. **光源として捕捉されない**。`block.properties` に溶岩がないので kind=0 になります（`release/shaders/lib/local_capture.glsl:48`）。さらに `LOCAL_SOLID` で `shape=1` に設定され（同 :24）、光源 kind のビットも `lampIndexImage` も書かれません（同 :51）。結果として、溶岩セルは光場のなかで **不透明な立方体**として記録されます。実際の液面は 8/9 の高さにあるのに、液面より上の 1/9 m を通る松明の光も遮られます。
2. **光はバニラのブロック光（ライトマップ）経由でしか届かない**。届いた光は `local_lighting.glsl:224` の `(1,0.56,0.25)·b³·2`（b = (16L+8)/256）で暖色に変換されます。ライトマップは flood fill の最大値なので、遮蔽も、面積による加算も、受光面の向きも扱えません。
3. **近くに登録済みの光源があると、溶岩の光が削られる**。`local_lighting.glsl:262-270` と `:316-318` の帰属ミックスは、ライトマップの光はすべて「既知の灯」から来たものとみなします。そのため、松明が届く範囲では溶岩由来の光を、弱い残差に置き換えてしまいます。
4. **単純に灯として登録しても破綻する構造**。8³ タイルごとの 12 枠を、タイル中心からの `level/(1+|d|²)` で選びます（`shadowcomp1.csh:67-97`、`local_light_grid.glsl:23-24`）。溶岩一マスを一灯として登録すると、枠の奪い合い、タイル境界での段差、面積の頭打ちが起きます。

### 数値（CPU、シェーダーの赤チャンネル放射照度単位。`receipt.json`）

基準形状は別エージェントの盆地フィクスチャ（`basin.py`）を読み取り専用で写したものです。白壁 z=366 上の 684 点を 0.25 m 間隔で取りました。

| 指標 | CPU 参照（面積分＋厳密な可視判定） | 1.8.0 の再現 |
|---|---|---|
| 石柱あり / なし（溶岩一マス、壁の中央値） | **0.638** | 1.000 |
| 石柱あり / なし（九マス） | **0.705** | 1.000 |
| 九マス / 一マス（柱なし） | **11.99** | 2.54 |
| 柱で完全に影になる壁の割合（一マス） | 16.2 % | 0 % |
| 10 m 上で 144 マス / 1 マス | **98.1** | 1.0 |
| 松明を一本置いたとき、壁に残る溶岩由来ライトマップ光（中央値・最小） | — | **35 %・0 %** |

実ゲームの観察（別エージェント、RTX 3080 Ti、1.8.0）でも同じ傾向が出ています。全光路が柱に遮られる壁領域で、赤の追加表示値は柱なし 77 に対して柱あり 68 でした。これは表示値の比であり、間接光と露出を含むので、上の表の量とは直接比べられません。言えるのは「遮蔽がほとんど効いていない」という方向性が一致していることだけです。

**仮に溶岩を点光源として 12 枠リストに登録した場合**（12×12 の溶岩湖、天井の受光線、松明 1 本）：

- 松明の光が届く 55 点のうち **15 点で松明が枠から押し出される**
- 8 m タイル境界で照度が **13.4 %（x=8）と 8.5 %（x=16）跳ぶ**。参照はどちらも 0.07 % 以下
- 湖の中央で参照の約 17 %（3.97 対 23.88）しか出ない。10 m 上では 144 マスでも 1.22 にとどまる（参照 12.35）。これは 16 マスのときの 1.43 より小さい値です

近距離では、点光源の近似 L·A·cosθ/r² が発散します（5 cm で 127 倍、1 m で +33 %）。1.8.0 の正則化カーネル 1/(0.38+d²) は発散しませんが、溶岩面はランバート放射（出射に cos がかかる）なので、斜め 45° の受光点では一定して過大になります（+27〜+107 %）。射程 14 m を越えると 0 です。

## 3. 提案：ワールド固定の露出面タイル（未実装・CPU で検証済みの部分のみ）

1. **捕捉**：`block.10120=minecraft:lava` を追加し、`local_capture` で `shape=10`（流体）とし、ビット 12–15 に液面高さの量子化値を書きます（同じ shape 同士の atomicMax は最大値になる）。`lampIndexImage` には登録しないので、**12 枠を構造的に消費しません**。`lampShapeBounds(10)` で `hi.y = h` とし、液面より上の光路は通すようにします。上面が露出しているかは `shadowcomp1` で「上のセルが shape 10 でも 1 でもない」ことから判定します。これは `LiquidBlockRenderer` の面カリングを、全面ブロックの隣接について写したものです。
2. **集約**：`shadowcomp1` は 8³ タイルごとにワークグループを回しているので、その中で主層（露出セル数が最多の y 層。同数なら下）を決めます。**64 bit の露出マスク、層、高さ、多層フラグ**を `lampListImage` の各行の **texel 15** に書きます。灯の数は最大 14 なので texel 0–14 しか使わず、texel 15 は空いています。OR と共有ヒストグラムだけで決まるので、実行順に依存しません。**新しい画像は増えません**。別エージェントの実測によれば、Iris の上限 16 枚をパックはすでに使い切っています。
3. **評価**：`lampLighting` に、灯リストとは別のループを追加します。受光点の**位置そのもの**を基準に、周囲最大 125 個の 8³ タイルを走査します。マスクが空でないタイルについて、放射範囲の AABB までの距離 d を求め、次のように使い分けます。
   - d < 2.5–3.5 m：セル単位
   - その外側、7–9 m まで：4×4 象限ごとのモーメント一致矩形
   - それより遠く：8³ 全体の矩形

   帯の中では線形に混ぜます。エネルギーは、縁で切り取った矩形に Lambert の閉形式を適用して求めます。可視率は、見えている矩形の中に置いた K 本の一様な光線（既存の `lampTransmissionCore` を利用）の比で推定します（ratio estimator）。光線の本数を予算で抑えても、エネルギー項は常に全量を計算するので、**枠の奪い合いは原理的に起きません**。
4. **縁（lip）の解析的クリップ（今回の新しい知見）**：溶岩源の液面は周囲の床より 1/9 m 低いので、浅い角度から見ると縁が液面を隠します。縁の矩形を受光点から液面へ中心投影すると、投影も軸に平行な矩形のままです。したがって、見えている部分は**矩形同士の交差**として光線なしで厳密に求まります。辺ごとに「溶岩がその先へ続くか」のフラグを持たせ、続く辺には縁を作りません。
5. **バニラとの二重計上を避ける**：帰属計算の `tracked` に溶岩も含めます（最も近い露出セルまでのタクシー距離で予測）。こうすると、松明を置いても溶岩の光が消されなくなります。
6. **明るさの較正**：今回は、一面の法線方向の光度が出荷版のレベル 15 の灯（11·(15/14)²）と等しくなるよう L を決めました。この場合、一面の光束は π·L で、等方な灯の 1/4 です。これは**芸術的なパラメータ**であり、色もまだ決めていません。

### 提案部分の数値

- **解析コントロール**：Lambert 多角形の式と Howell の閉形式（平行な矩形の角の真上にある微小面）の差は、高さ 0.05–16 m で 2.3×10⁻¹⁶ 以下。256² 中点則との差は 2.9×10⁻⁶ 以下。天井面上で積分した光束は π·L·A を 1.7×10⁻⁴ の精度で再現した。
- **近距離・遠距離**：遮蔽のない解析タイルと総当たり積分の差は、5 cm から 32 m まで（一マス・九マス、真上・45°）で **1.5×10⁻³ 以下**。
- **縁クリップ**：柱なしでの残差は、参照の分割数 n=12/24/48/96 に対して 5.4/2.5/1.25/0.62 % RMS と、1/n で減っていく。これは参照側の誤差であり、クリップ自体は厳密。縁を無視すると、一マスで RMS 32 %・光束 +22 %、九マスで 13.7 %・+11 % の誤差が出る。
- **柱の半影**（盆地、一様な K）：一マスで K=1/4/9/16 のとき RMS 26.7/11.2/7.2/4.7 %、九マスで 39.9/12.4/7.2/5.6 %。光束の誤差は K≥4 で ±1.7 % 以内（K=1 では最大 +2.9 %）。
- **等寄与層別**（解析式の二分法で、各層が同じ寄与を持つように切る独自の求積）：一様な層別との差は 1 ポイント以内で、改善はほぼない。
- **12×12 の湖**：4³ でも 8³ でも RMS 0.54 %・最大 1.2 %。タイル境界での段差は参照と同じで、継ぎ目はない。
- **自然の溶岩溜まり**（別エージェントの `natural-pool.json` の 25 セル。受光面は仮想の平面）：天井 5 m で tile1/4/8 が 0.5/2.3/9.1 % RMS、東壁で 2.5/7.5/12.4 %。高さを変えると、8³ が 4 % を切るのは約 8 m 以上、4³ は約 3 m 以上。**階層方式は 1.5–12 m の全域で RMS 3.2 % 以下・最大 9.8 % 以下**。5 cm 刻みの線上で隣り合う点の段差は平均の 2.6 % で、参照自身の段差 4.0 % より小さく、連続している。

## 4. 実装に進むか（go / no-go）

**GO（次の段階に限る。本番投入ではない）**

1. 捕捉だけの変更：ID、shape 10、液面高さ、texel 15 の集約。照明は変えずに、デバッグ表示で実ゲームの盆地と自然溜まりのマスクを確認します（起動は Codex の担当）。
2. 遮蔽のないエネルギー項：縁クリップと階層マスクを使う方式。CPU では RMS 3 % 程度です。
3. 可視率：近い・中くらいのタイルは K=4（柱の半影で RMS 約 12 %）、遠いタイルは K=1。予算に余裕があれば K=9（約 7 %）にします。

**NO-GO**

- 溶岩一マスを 12 枠の灯として登録する案：枠の奪い合い、13 % の継ぎ目、面積の頭打ちを実測で確認しました。
- 等寄与層別：効果がほとんどなく、GPU 上の二分法のコストに見合いません。
- 4³ のモーメントを新しい画像に保存する案：Iris の 16 枚上限に当たります。1×1 の `lampExposureImage` を既存画像の空きに移すなどして枠を空けた場合に限り、側面（溶岩の滝）や多層への対応とあわせて再検討する価値があります。

**未確定（GPU と実ゲームでの確認が必須）**

- **GPU コストは測っていません。** 目安として、近いタイル 1 個に K=4 を使うと影の光線が 4 本です。1.8.0 の円盤 3 点サンプル 1 灯分の約 1.3 倍に当たります。これに最大 125 回のテクセル取得と、近いタイル 1 個あたり最大 64 回のセル単位 Lambert 計算が加わります。README によると、1.8.0 は松明 1 本の場面ですでに 49.6 → 31.3 FPS です。GPU ハーネスで計測するまでは、リリースを判断できません。
- 実ゲームでの受け入れ条件の案：盆地で露出を固定し（`LAMP_ADAPTATION=0`）、`measure_wall.py` の `fullyBlocked` 領域で直射成分がゼロになること（残るのは間接光と残差だけ）。九マス / 一マスが直射で約 12 倍の方向に変わること。松明を加えても溶岩側の壁が暗くならないこと。

## 5. 既知の制約

- 扱うのは上面（+Y）だけです。溶岩の滝などの側面や、1 タイルに複数の層があるものは、1 テクセルの詰め込みでは表現できません（フラグを立ててバニラに戻す設計）。
- 流れている溶岩の上面は傾いていますが、水平な量子化高さで近似しています。最大で約 34° の傾き、面積は 1.2 倍になりえます。この誤差は今回のレシートでは**定量していません**。
- 柱などの外部遮蔽物は K 本の光線でしか見ていません。半影の誤差は RMS 5–12 % です。
- 1.8.0 の再現は、壁の前の空気セルによるフラット照明です。スムースライティングと AO は含めていません。松明の flood fill は、開けた部屋のタクシー距離で近似しています。
- 参照の可視判定は、全面ブロックと溶岩の箱だけについて厳密です。ハーフブロック、階段、扉、葉は含みません。自然溜まりは平らな床に沈んでいると仮定し、受光面は仮想の平面です。
- 色、露出、トーンマップは扱っていません（赤チャンネルのスカラー値のみ）。溶岩テクスチャのアニメーション（still は frametime 2 の 38 コマ往復、flow は frametime 3）も、明るさの変動として扱っていません。
- カメラ相対の 19–24 m のフェードとグリッド範囲（±24–32 m）は残ります。連続ではありますが、カメラ位置には依存します。
- 文献の DOI と URL は、このセッションでネットワーク確認していません。

## 6. 計装した試験と実際の Minecraft の区別

| 種類 | 何を測るか | 含まないもの |
|---|---|---|
| この CPU レシート | 理想化したボクセル形状での、シェーダー単位の放射照度。1.8.0 は数式を numpy で再現したもの | Iris、ドライバ、露出、トーンマップ、間接光、テクスチャ、実際の光場 |
| GPU ハーネス（`make check` 等） | コンパイル、リンク、GPU 上の数値 | 今回は**実行していない** |
| 私設の観測版（別エージェント） | 実ゲームで光場に何が渡るか（例：水中アトラスへの記録） | 配布版ではない。描画結果は変わりうる |
| 実際の Minecraft（`baseline-180/`） | 実画面の表示 RGB の中央値 | 直射と間接の分離。絶対的な放射照度 |

CPU の比率は「どちらの方向に、どれくらい変わるべきか」の予測です。実ゲームの表示値と絶対値で一致させることを目標にしてはいけません。
